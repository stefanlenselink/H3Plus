# Artifacts You Must Provide Yourself

> **This repository intentionally contains no firmware.**
> For legal reasons, no firmware images, flash dumps, or derived binary artifacts are
> published here. The folders `BIN/`, `FW/`, `Dumps/` and `work/` referenced throughout
> the documentation **do not exist in this repo** — you must create them yourself.
>
> This page explains what each folder is expected to contain and exactly how to acquire
> or generate every artifact the tools and findings refer to.

## Folder overview

| Folder | Referenced by | Contents | How to obtain |
|---|---|---|---|
| `BIN/` | patch tool, `Tools.md`, findings ch. [02](findings/02-artifact-inventory.md), [12](findings/12-bluetooth-5-patching-tool.md) | Kenwood/CH340 serial-flash images (`*.bin`, e.g. `TD-H3-PlusV1.0.50.bin`) | Vendor update package (see 1) |
| `FW/` | findings ch. [02](findings/02-artifact-inventory.md), [04](findings/04-container-formats.md), [05](findings/05-lfsr-cipher-and-key-recovery.md) | USB-C upgrade packages (`*.fw`, e.g. `TD-H3-PlusV1.0.50.fw`) | Vendor update package (see 1) |
| `Dumps/` | patch tool, findings ch. [16](findings/16-flashing-and-hardware-dump.md) | Full 1 MiB SPI NOR dump of **your** radio (`dump_internal.bin`) | Dump it yourself with jl-uboot-tool (see 2) |
| `work/` | almost everything | Scratch space: decrypted images, patched outputs, sector exports | Generated by the tools (see 3) |

Create them at the repo root: `mkdir BIN FW Dumps work`.

## 1. Vendor firmware (`BIN/`, `FW/`)

Download the official H3 Plus firmware update from TIDRADIO:

- Official site & download page: <https://www.tidradio.com/> (search "H3 Plus" →
  "Firmware Update"). The download is a ZIP such as
  `H3 Plus Update-Type-C.zip` (USB-C package, contains a `.fw`) or
  `H3 Plus Update-CH340 Tutorial.zip` (serial package, contains a `.bin` plus the
  CH340 driver and the `updata.exe` updater).
- Put the `.bin` files into `BIN/` and the `.fw` files into `FW/`.
- Keep the whole ZIP — the updater executables inside it are the official flashing
  path and are referenced in [findings ch. 15](findings/15-official-tooling.md).

The exact version used throughout the findings is **v1.0.50**
(`TD-H3-PlusV1.0.50.bin` / `TD-H3-PlusV1.0.50.fw`). Older versions (1.0.32–1.0.47)
are also available from the vendor and were used for the differential analysis in
[findings ch. 14](findings/14-differential-analysis.md).

> Note: the vendor ZIPs, CPS software and updaters are **not** redistributed here
> either — acquire them from the official TIDRADIO pages.

## 2. Hardware flash dump (`Dumps/`)

The single most important artifact is a full 1 MiB dump of **your own radio's**
internal SPI NOR. It is device-specific (BT identity, pairing records, the 32
device bytes at `0x0C8FE0`) and cannot be downloaded — you must read it.

1. Enter the JieLi USB bootloader (see the step-by-step in the
   [README](README.md#step-by-step-alter-your-own-firmware): hold **PTT + `3`**
   — or **`8`** on later firmware — while powering on with a USB-C data cable in
   the **side** port).
2. With [jl-uboot-tool](https://github.com/kagaimiq/jl-uboot-tool) installed
   (Linux, `sudo`), run:

   ```console
   $ sudo python3 jluboottool.py
   =>JL: read 0x00000000 0x100000 Dumps/dump_internal.bin
   ```

3. Verify: the file must be exactly `1,048,576` bytes and its first 64 bytes must
   match the header of the vendor `.bin` (see
   [findings §12A.4](findings/16-flashing-and-hardware-dump.md)).
4. **Back this file up off-machine.** It is your brick insurance and contains your
   unit's unique BT identity.

Optionally also dump the VM/settings area (plaintext, holds BT names & pairing):

```
=>JL: read 0x000C9000 0x1000 Dumps/vm.bin
```

Full background: [findings ch. 16 — Hardware Flash Dump](findings/16-flashing-and-hardware-dump.md).

## 3. Derived artifacts (`work/`)

Everything in `work/` is generated, never downloaded. Typical pipeline:

```bash
# decrypted UBOOT (LFSR stream; phase 32591 for .bin, 31567 for .fw)
# writes <name>.p<phase>.dec next to the input and prints an entropy report
python tools/jl_decrypt.py BIN/TD-H3-PlusV1.0.50.bin 32591

# decrypted app region (SFC/ENC hardware scrambler, chipkey 0xF181)
python tools/jl_sfcenc.py BIN/TD-H3-PlusV1.0.50.bin work/app_dec.bin

# patched output + per-sector flash files (the patch tool does the crypto internally)
python tools/patch_h3plus_firmware_bluetooth.py BIN/TD-H3-PlusV1.0.50.bin work/patched.bin --sectors=work/sect
```

`work/` is scratch — feel free to `.gitignore` it.

## 4. The 32 device-specific bytes at `0x0C8FE0`

The vendor `.bin` carries `0xFF` at flash `0x0C8FE0`–`0x0C8FFF` where your live radio
holds real per-unit data. **A full-image reflash of a stock-derived image erases it.**
If you ever flash a full image, splice your dump's block back in first:

```python
raw  = bytearray(open('work/patched.bin', 'rb').read())
dump = open('Dumps/dump_internal.bin', 'rb').read()
raw[0xC8FE0:0xC9000] = dump[0xC8FE0:0xC9000]
open('work/patched_safe.bin', 'wb').write(raw)
```

The per-sector route (`--sectors`) never touches that block and is the safer default.
Details: [findings §9A.38](findings/12-bluetooth-5-patching-tool.md).
